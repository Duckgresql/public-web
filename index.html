The split

One database can't do both.
So we stopped pretending.

Postgres is the standard for transactions. DuckDB is unmatched for analytics. The mistake is forcing one to do the other's job.

Postgres · OLTP

Built for state, not for scans.

Row storage is great for transactional reads and writes. It's the wrong shape for aggregating millions of rows.

  • Row-oriented storage is inefficient for large analytical scans.
  • Heavy aggregations compete with your production workload.
  • Scaling analytics usually means another database — and a pipeline to keep it in sync.
DuckDB · OLAP

Built for scans, not for state.

Columnar and parallel — phenomenal for analytics. But it was never designed for concurrent application writes.

  • Single-writer model limits concurrent write throughput.
  • No native horizontal scaling for read-heavy production traffic.
  • Hard to wire up to a transactional source of truth without DIY plumbing.
How it works

Two engines.
One connection.

Connect once. Duckgresql routes each query to the right engine — Postgres for transactional reads and writes, DuckDB for analytical scans — and joins across both when you ask it to.

01 · Connect once

One endpoint, one SDK. Drop it in where Postgres or DuckDB sits today.

02 · Route automatically

Transactional queries land on Postgres. Analytical scans land on DuckDB. Override anytime.

03 · Join across both

Mix tables from either engine in a single SQL statement. The planner handles the rest.

Example

One query.
Both engines.

Reference any table from either engine. Duckgresql plans the join, pushes work down, and returns one result set.

  • Standard SQL — no new dialect to learn.
  • Live Postgres data, columnar-fast aggregates.
  • No replication scripts, no warehouse syncs, no stale data.
cross_engine_join.sql 
-- Active Pro users joined with their last 30 days of activity
SELECT
  u.email,
  u.plan,
  s.events_last_30d,
  s.last_seen_at
FROM postgres.users u            -- OLTP: live application state
JOIN duckdb.user_events_30d s   -- OLAP: precomputed columnar aggregate
  ON s.user_id = u.id
WHERE u.plan = 'pro'
ORDER BY s.events_last_30d DESC
LIMIT 100;
